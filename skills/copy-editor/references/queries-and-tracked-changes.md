# Queries and tracked changes

The edit is a proposal. The author's acceptance is what makes it a document. This
file is the etiquette and the mechanics that keep the relationship working.

## Query format

One line, at the location, with a reason and a proposed fix:

```
Q7 - p14, para 2: "shall" here, "will" in clause 9. Policy docs use "must".
     Propose "must" in both. Confirm?
```

Rules: number them, never bundle two issues, always propose something, and never
phrase a query as a correction. "Is this the right GSTIN?" gets an answer;
"wrong GSTIN" starts an argument.

## What becomes a query, always

| Item | Why |
|---|---|
| Any number, price, date or percentage | You cannot verify the source |
| Names of people, companies, products | Spelling is the author's to confirm |
| Legal terms and citations | Meaning changes with a word |
| A statement that contradicts another document | One of them is wrong and you do not know which |
| Anything that reads as a factual claim about the world | "The largest in India" needs a source |
| A deletion of more than a sentence | Deleting someone's paragraph is an edit, not a correction |

## Tracked changes etiquette

- **Use suggesting mode or tracked changes, always.** An untracked edit to someone else's document is a silent change.
- **One reviewer name.** Mixed identities in the markup make the accept/reject pass a puzzle.
- **Batch the accept.** Let the author accept or reject in one sitting; do not ping per change.
- **Never resolve your own comments.** The author resolves, or they stay open and visible.
- **Keep a clean copy** after acceptance, with the changes accepted and the queries archived in the ledger.

## The sign-off

Before you call it done:

1. The author has accepted or rejected every tracked change.
2. Every query is answered, or explicitly deferred with a name against it.
3. The style sheet is updated with any new decision.
4. The terminology ledger has the new terms and their locations.
5. The version you proofed is the version being sent - confirm the file name and date.

## Escalation, when it is contested

| Situation | Move |
|---|---|
| Author disagrees with a house-style rule | Apply the rule, note the exception request on the sheet, let the owner decide |
| Two documents state different facts | Query both owners; do not pick the newer one |
| A legal reviewer overrides the sheet | Follow the reviewer, record the override with the date |
| The client wants a rewrite, not an edit | Say so, and route to `content-writer` |
| The deadline does not allow the full pass | Do the proof, list the passes not done, and say what risk that leaves |

## Anti-patterns

- **Silent corrections.** The author learns nothing and the error returns next document.
- **Queries without proposals.** The author does the work twice.
- **A 60-item query list on a two-page brief.** Decide what the sheet covers and query only what it does not.
- **Accepting changes on the author's behalf** to hit a deadline. It removes the only record of what was decided.
- **Editing a copy that is not the latest.** Confirm the version before the first correction, not after.
